# Code layout

Back to the [README](../README.md).

Where the code lives, and where a new feature's pieces go. The office used to grow by adding to the middle of a few big files: the server's message switch and the page's store. Each of those is a registry now, and a feature is a module of its own plus one line in each list it joins. If a change has you editing the middle of `server.ts`, the store or `protocol.ts`, it probably belongs somewhere else.

There are three parts: `src/client` (the pages, built by Vite), `src/server` (Node) and `src/shared` (types and pure code both use, with no Node imports).

## The registries

| What | Where a feature adds itself | Its list |
| --- | --- | --- |
| HTTP routes | its routes in `src/server/http/routes/<name>.ts` | `http/routes/index.ts` |
| WebSocket messages | a handler map in `src/server/ws/handlers/<domain>.ts` | `ws/handlers/index.ts` |
| Page state | a slice in `src/client/state/slices/<name>.ts` | `SLICES` in `state/slices/index.ts` |
| Settings sections | a row in `src/shared/settings-sections.ts` and its builder | `SECTION_BUILDERS` in `ui/settings/` |
| Project tabs (the 1D view's pages) | a `registerTab` call in the feature's own tab module (`ui/<name>/tab.ts`) | `src/client/tabs/index.ts` |

Each is explained where its code is described below; [Adding a project tab](#adding-a-project-tab) has the tabs'.

## Client

Every page is an entry of its own in `vite.config.ts`, an HTML file with its script beside it in `src/client`: the 1D view (`lite.html`, `lite.ts`, at `/lite`: where every project opens, on its Command Center), the 2D Office view (`pixel.html`, `pixel.ts`, at `/pixel`, reached only by the 1D view's **Go to Office**), Home (`start.ts`, at `/start`: where the wordmark and a bare `/` go), the Projects page (`home.ts`, at `/home`), Clients (`clients.ts`), The Firm (`firm.ts`), the docs (`docs.ts`), the phone version (`m.ts`), first-run setup (`setup.ts`) and the sign-in pages (`login.ts`, `claim.ts`, `join.ts`). The 3D office that used to be at `/` (`main.ts`, three.js, and its `core/`, `features/`, `input/`, `world/`, `player/`, `sound/` and `models/` folders) is gone: `/` redirects to the 1D view (`server/http/routes/pages.ts`). `tests/client-structure.test.ts` checks it stays gone and that every module under `src/client` is loaded by one of the pages.

### Folders

- **`state/`** is the store. `store.ts` declares the core fields (who you are, the people, the projects, and the project you're on with its workers, screens, boards and queue), and `core.ts` keeps them up to date. Everything else is a slice in `state/slices/`: a module that adds its fields and topics to `Store` and `Topics` (`declare module '../store'`), sets where they start (`init`), and says what it takes in from each server message (`on`) and from each project you arrive on (`enter`). Slices run in the order of `SLICES` in `state/slices/index.ts`, which is the order their topics fire in, so a new one goes at the end. A page follows a topic with `store.on('<topic>', fn)`. What the browser remembers between visits is `persist.ts`.
- **`ui/`** is the pages' shell: the ☰ menu (`menu.ts`, its items `menuitems.ts`), the views' buttons (`viewpick.ts`: Go to Office and Return to Project) and the windows (terminals, changes, the queue, and the GitHub windows in `ui/github/`). ⚙️ Settings is `ui/settings/`: a builder per group of settings (`you.ts`, `notify.ts`, `workers.ts`, `building.ts`, `project.ts`, `office.ts`, each giving back its nodes and an `off`), and the full page (`page.ts`, the 1D view's ⚙️ Settings tab; `flat.ts` wires it to a flat session and sends the 2D view and the home page there). Its sections, their order and their addresses (`/lite?tab=settings&section=<id>`) are `src/shared/settings-sections.ts`: a new section is a row there and a builder in `SECTION_BUILDERS` (the typecheck wants both), and every settings link uses `settingsHref`. Each module imports its own stylesheet (`import './palette.css'`), as a feature's `ui.ts` does (`import './ui.css'`).
- **`shared/`** (`src/client/shared/`) is what the pages share: the tab title and hiring, and what the 1D view (`lite.ts`, at `/lite`) and the 2D Office view (`pixel.ts`, at `/pixel`) both use: their connection and coming in (`session.ts`), what they do with a worker (`workers.ts`), and the project picker (`floors.ts`). The home page (`home.ts`, at `/home`) is in `src/client/home/`: the project cards (`projects.ts`), their ⏸ / ▶ state icons and the one Pause all / Resume all button (`run-state.ts`, its pure logic in `run-state-logic.ts`) and the statistics (`stats.ts`, from `GET /api/home/stats` in `server/home-stats.ts`). The 2D Office view is in `src/client/pixel/`: the camera (`camera.ts`), the still office and its props (`office.ts`, `props.ts`), the people and desks drawn every frame (`people.ts`), what can be clicked (`hotspots.ts`), what's drawn sharp over it (`overlay.ts`) and its HUD (`hud.ts`, `game.css`). Its top bar is the Portal bar's shape (OFFICE · the project, **Return to Project**, the icons) and everything about the office itself is on its toolbar over the canvas (`pixel.html`, `pixel.css`). The windows both views open, the whiteboard and the bookshelf among them, are in `ui/`.
- **`ui/app-workspace/`** is the Developer view ([Developer view](site/using-the-office/developer-view.md); the code keeps the name app workspace): one project tab from the tab registry (`tab.ts`: `app`, hidden from the navigation; the retired sections' ids `requirements|decisions|review|release` stay registered, hidden, and open the Project Management page with their list), which loads the rest on first show; `tab.ts` also puts the **Developer | Project Management** switch (`view-switch.ts`, small, with the page's first tab) in the top bar right after Go to Office, so it stands in the same place on every project page, and marks it on every tab change (`tabs/host.ts` `onProjectTab`). The rest: the workspace (`shell.ts`: the project's name and the canvas's two views, Model preview by default and Live preview, `body.aw-on` while it shows and `&ws=app` in the address), the live canvas (`canvas.ts`, the Live app tab's viewer on the served revision), the **docked coordinator chat** (`dock/`: `index.ts` lends the team-lead panel its header, its cards and the explorer's selection as context through `ui/lead-panel/dock.ts`, and sends Request a change through the one intake with the element reference, the revision viewed and a key per message; `cards.ts` the request with its receipt (execution, checks, preview and review kept apart), Please try this and the inline decision cards; `logic.ts` the pure words: this session's changes, receipts, chips, the lead's note), the fallback Request a change dialog (`requests.ts`, also the POST every entry point uses), the Developer changes (`ui/dev-changes/`: `feed.ts` the page's one feed of `GET /api/dev-changes`, `view.ts` the execution pill, the four facts, the revision strip, the rows and the lifecycle's actions (Cancel, Retry, Mark superseded, Confirm / Dismiss), `pm.ts` the same record on Project Management's Approvals; the explorer's revision line offers the active change's candidate, `explorer/revision.ts`), the business decision cards with their related artifact and answer (`decision-cards.ts`, drawn one by one in the chat), guided validation (`validation.ts`: the guided checks of the running version under the Live preview, Try it, the marks and their dialog) with its calls and feed (`validation-api.ts`, asked only once the Live preview shows; it also posts a try card's marks) and what they read (`data.ts`: the live app slice `state/slices/liveapp.ts`, the business status feed, Needs you's snapshot filtered by `shared/app-workspace/business-decisions.ts`, the progress bar's route, the brief, the pull request list, the roster, the dev-changes feed; no timer). The address's rules and its words (the views' names, `ws=app|dev` and `ws=eng|pm`, the retired sections, the business status's missing lines said shortly, the stage) are pure, in `shared/app-workspace/`; `shared/address.ts` reads `ws` through `workspaceTab`, and `tabs/host.ts` `openProjectTab` lets a tab module show another tab the way the page does.
- **`ui/app-workspace/explorer/`** is the Developer view's explorer (its left sidebar, imported by `shell.ts` with the first show; it opens the app's first page in the Model preview (`first-page.ts`) and reports what's open to the chat as context): `index.ts` the sidebar (the business tree or **Show all files**, the search over the whole tree or every file, the selected item's bar with Open in the live app, Request a change and an admin's Change this, width, collapse (the collapsed icon rail in `rail.ts`) and the switch remembered per viewer, the phone's drawer, main's newest commit asked on open, focus and a live-revision change, the stale note and Show it: the open levels read again, the changed rows dotted), `revision.ts` the revision line (main or the live app's revision, where the live app is, stale), `tree.ts` the WAI-ARIA tree (keyboard, type-ahead, the visible rows, matching on titles and details), `pane.ts` what opens in the canvas's place (a page's Model preview through `ui/model/page-frame.ts`, never the live frame; data and logic diagrams; a file's text or picture; a document's card), `element-ref.ts` what a request from the pane or the bar points at (page, or page + widget name with `$Type`/`$ID` from the page's facts, the chip, the shared-snippet impact), `pick.css` Select element's chip, `docs.ts` the Documents, Process map and Design groups from the documents answer, `doc-card.ts` a document's card (revision, git provenance, versions, formats and representations side by side, supporting, related, review rounds, status with its source), `dots.ts` the changed rows' dots after a newer revision, `api.ts` its requests, kept per revision. Its rules are `shared/app-explorer.ts` and `shared/app-documents.ts` (with `shared/app-documents-rules.ts`); while the switch is on its rows carry `data-words-exempt`. The Model preview it shows is `ui/model/`'s: `page-preview.ts` the page written out as HTML (bounded: `preview-parts.ts` holds the sample-row depths, the widget budget, conditions read and tagged, cases of one value grouped, element labels; with `marks` each named widget carries `data-mx-*` and the drawing returns a report of what it left out), `preview-css.ts` its stylesheet (Atlas-like, Atlas helpers, the bounded marks, the pick outlines), `page-frame.ts` the sandboxed frame (the report line; with `pick`, Select element: `allow-scripts` only, a nonce per document, the selection kept by document + name), and `preview-pick.ts` the frame's script and the page's postMessage checks; the request types are `shared/page-facts.ts`.
- **`start/`** is Home (`start.ts`, at `/start`): its sections (`sections.ts`) put on the page by `view.ts`, what it reads (`data.ts`: `GET /api/start`, the budget and the clients, asked again only on a change) and its Portal left navigation of the office's pages (`nav.ts`). Its rules are `shared/start.ts` and its server side `server/start/` (each project's red Needs-you items through notify-teams' `floorNeeds` and `redItems`, as the desktop tray's, the stuck and failing counts, the live apps, the recorded milestones and the health), behind `http/routes/start.ts`.
- **`pixel/`** is the 2D Office view's drawing and HUD (see above), and **`home/`**, **`firm/`**, **`mobile/`** and **`first-run/`** are the other pages' own parts.

### Stylesheets

Every page's sheet (`lite.css`, `pixel.css`, …) pulls in `styles/base.css` (the colors, the reset, panels, buttons and the window frame). Every other sheet sits next to its module and comes in with it. A module's sheet loads in no fixed order against `base.css`, so a module rule that overrides a base rule of the same specificity has to be more specific, or live at the end of `base.css` with the others there.

Colors are tokens: the custom properties at the top of `base.css`, each with what it's for (`--card` on `--paper`, `--line` round it and `--edge` under it, `--bad-ink` for red text, `--good-soft` behind good news, and so on). A sheet the 1D view loads names its colors with them rather than a hex, because the 1D view's color themes (`ui/colortheme.ts`, which sets `<html data-theme="dark">` or `"terminal"`) only change the tokens: their values are in `styles/themes.css`, and the Terminal theme's shapes (square corners, bracketed buttons, scanlines) in `styles/theme-terminal.css`. The Clean and Portal pairs are one family: Clean's rules (`styles/theme-clean*.css`, `ui/clean/` for the emoji) are under `html:is([data-theme^='clean'], [data-theme^='portal'])`, and Portal adds its tokens and parts (`styles/theme-portal*.css`), its top bar (`ui/portal/`, pieces marked `.pt-only` that only Portal shows), the 1D view's Portal layout (`ui/portal/layout.ts`: the left navigation `nav.ts` with its pure `nav-logic.ts`, the page header `pagehead.ts`, the Overview's cards `overview.ts` with `overview-logic.ts`, its Needs you card `needs-card.ts` with `needs-logic.ts` (fed by the Needs-you strip's list, `ui/needsyou/feed.ts`) and its Project brief card `brief-card.ts`; the page's own pieces it shows elsewhere are moved, not copied, by `slot.ts` and moved back in the other themes) and Home's Projects page (`home/portal.ts`, its filter and sort in `home/portal-logic.ts`, its card `home/project-card.ts`, which the Clients page draws too). The values in `base.css` are the Default (Fun) look.

## Server

- **`server.ts`** is the composition root: `startServer` builds the office's context a stage at a time, starts the hook server, opens the projects, and hands the context to the HTTP handler and the WebSocket.
- **`office/`** is that context (`Ctx` in `office/context.ts`: the building-wide services, sending to browsers, the projects, the people in the office, going between projects, and the checks before something happens) and the pieces that make it.
- **`ws/`** takes the sockets. Each domain's messages are handled in `ws/handlers/<domain>.ts`, a map from message type to handler that `satisfies HandlerMap<ItsClientMsg>`, and `ws/handlers/index.ts` puts them all in one `HandlerMap<ClientMsg>`: a message type with no handler, or a handler for a type that doesn't exist, fails the typecheck. The same file lists the features that keep something per person on a project (`features`: what each lets go of when someone is `leaving` a project, and once their socket has `closed`) and the pieces of what someone arriving on a project is sent (`views`, one for each field of `FloorView`, put together by `office/views.ts`).
- **`http/`** answers HTTP from a route table. Each file in `http/routes/` exports its routes, and `http/routes/index.ts` lists them in the order they're tried. Every route says its `auth` (`public`, or `session` for a signed-in browser), and the `Route` type won't let you leave it out.
- **`hooks/`** is the loopback-only hook server the workers call: their agents' hook events (`/hooks/<provider>`), the board agents' queue (`/office/queue`) and `office-workers` (`/office/workers`; its Marketplace requests, `office-workers marketplace` and the `office-marketplace` command the office writes beside it, in `hooks/office-marketplace.ts`, the command's parts in `bin/office-marketplace.js`).
- **`workers/`** is the worker manager (`WorkerManager` in `workers/manager.ts`) and its pieces: worktrees, pull requests, tasks, terminals, ACP workers, and saving to `workers.json`. `src/server/workers.ts` re-exports it for the modules that imported it from there.
- **`providers/`** holds one adapter per agent CLI (see [Adding an agent provider](#adding-an-agent-provider)).
- **`tunnel/`** is `agent-office tunnel`, the one part that runs on someone's own computer instead of the office's: it asks the office for the workers' web servers (`/api/services`, in `http/routes/services.ts`) and listens on each one's port there. It imports nothing from the office but what the two say to each other (`tunnel/wire.ts`) and the cookie's name.

- **`flow/`** is the workflow engine, for work that's a list of steps that must survive failures and restarts (see [Workflows](site/automation/workflows.md)). A workflow (`WorkflowDef` in `flow/types.ts`) is named steps, each `async (ctx) => partial state update`, joined by edges: a step id, or a function of the state that picks one (a gate), with `END` to finish. `FlowEngine` (`flow/engine.ts`) runs it against one state per run and checkpoints the run (`RunRecord`: step, state, status, tries, loop counts, usage, history) through a `CheckpointStore` (`flow/store.ts`: `<data>/flows/<workflow>/<run>.json`, written atomically) after every step; a run that was `running` when the office stopped loads as `interrupted`. A step may declare `done(state)` (skipped when true, so resuming is safe), a `retry` policy (`flow/retry.ts`: exponential backoff with jitter, `retryOn`, e.g. `transientError`) and a `cache` (a key and a TTL). Loop guards (`limits.maxSteps`, `limits.loops['from->to']`) and budgets (`limits.budget`, `limits.check`, against what steps `report`) stop a run as `needs-attention`; a step returning `interrupt(payload)` stops it as `waiting` until `resume(runId, value)` hands the value to that step. Its events (`run-started`, `step-started`, `step-finished`, `step-failed`, `run-paused`, `run-finished`) are what the audit log (`auditFlows` in `flow/index.ts`) and anything else subscribe to. `flowsOf(ctx)` is the office's one engine; a feature registers its workflow there and starts runs, as the wizard's `JobBook` (`wizard/job.ts`) does, and `GET /api/flows` (`http/routes/flows.ts`) lists them. The engine is meant to grow without changing that shape: typed interrupts with options (`waiting.payload`, the `run-paused` event), shared state with reducers (`WorkflowDef.merge`), a pipeline whose gates are conditional edges, tracing (the events and `history`), and forking a run from a checkpoint (`HistoryEntry.seq`).

- **`wizard/`** is ✨ New project: the setup's steps (`steps.ts`) run on the workflow engine (`job.ts`), and every external action that can't simply be done again (creating or deleting the GitHub repository, cloning or deleting the folder) is an operation record (`shared/setup-operations.ts`, stored by `operations.ts` in `<data>/wizard/operations/`), its intent written before the command and its outcome after, through the acknowledged critical write (`flow/critical-write.ts`: an awaitable write that rejects on failure; file fsynced, then an atomic rename, the folder fsynced where the platform allows; process-crash safe, power loss not claimed). Background writes (`flow/store.ts`) stay for state the office can work out again. An outcome nobody confirmed stops every later step (`JobBook.step`) until `reconcile.ts` settles it by looking (at start, before a Retry, and on Check GitHub again), and only a confirmed create gives Cancel & undo (`cancel.ts`, `ownership.ts`) the right to delete. And **`wizard/planner/`** is the Chief Analyst drafting the project brief with the person: its drafts in the office's data (`drafts.ts`), the capped `claude -p` calls (`cli.ts`, `engine.ts`) or the deterministic test planner (`fake.ts`), behind `/api/brief/*` (`http/routes/brief.ts`). The brief's shape, its honesty rules and what it becomes in the project (intake answers, the Stage 0 rows, `docs/project-brief.md`) are shared code (`shared/brief.ts`, `shared/brief-map.ts`); the page is `ui/wizard/new/`, loaded only when it's opened (`ui/wizard/open.ts`). A draft's source folder (Migrate an app, Change an existing app) is `shared/source-folder.ts` (what is skipped, the summary, the planner's file index), `wizard/source-folder.ts` (refused paths, the walk and the scan, fs/promises only), `wizard/source-snapshot.ts` (the import: a fresh staging copy hashed into `sources/legacy/<name>.manifest.json`, checked, then swapped in under an operation record that the next run recovers), `http/routes/source-folder.ts` and `wizard/source-step.ts` (the import into `sources/legacy/` after the intake step), with the page's `ui/wizard/new/source-folder.ts`. Local only (Where the code lives) is `wizard/local-only.ts` (the settings and issue steps' local-only parts, the Discovery file) and `server/local-only.ts` (the project file's `localOnly`, read by `github.ts` to refuse GitHub calls and by the roster's hire context); a migration's Discovery wording is `shared/discovery-migration.ts`.

- **`team-server/`** is Mendix Team Server for a project ([On Mendix Team Server](site/get-started/first-project.md#on-mendix-team-server), words and rules `shared/team-server.ts`): `api.ts` the Projects API v2 (`POST /projects`, its job followed to the app's id, every refusal in words: the scope, the company's policy, the name, the proxy), `git.ts` git with the Mendix token for one command (command-scoped GIT_CONFIG_* resetting git's credential helpers and adding one, scoped to Team Server's host, that reads the token from that child's environment; output redacted), `sync.ts` main and Team Server brought together fast-forward only (push and confirm with `ls-remote`, Studio Pro commits pulled to origin's main, both moved said and nothing pushed, the history notes merged with Team Server's before they're pushed, Team Server not answering said as `unreachable`), `studio-copy.ts` the Studio copy Edit in Studio Pro opens (`<owner>/.studio-pro/<name>`, origin Team Server, made and fast-forwarded with the token per command; registered as a Studio target, `studio/targets.ts`), `environments.ts` the app's Mendix Cloud environments from the Deploy API v4 (read-only, cached, the token only in the header), `adopt.ts` the commit that adopts Team Server's history without changing the tree and the CLAUDE.md rule, `connect.ts` Connect to Team Server for a local-only project (one commit built with a temporary index, origin first, then Team Server), `project.ts` the `teamServer` record in `agent-office.project.json`, `audit.ts` the `team-server.*` audit lines, and `index.ts` the office's one (`teamServerOf`: the view, a sync per project at a time, connect, `<data>/team-server/<floor>.json`) with `startTeamServer` in `office/timers.ts` (a sync soon after `floor-sync/bus.ts` origin news, which the local merge now sends, within seconds for a project with no GitHub; one project per slow tick; every 30 s while Studio Pro has the Studio copy open; a network check and a back-off when Team Server doesn't answer, and a pause after a wake from sleep; the team told *main moved (Studio Pro commit)* on a pull). Ready to create's Claude sign-in check (hiring the team runs on the creating account's own sign-in: shown before Create, the start refused before anything is made) is `wizard/claude-signin.ts`, read by `http/routes/wizard.ts`. The wizard's side is `wizard/team-server-step.ts` (the Portal app made or linked in the repo step, saved as it goes; the remote and the adoption after the clone; the record and rule in settings; main to Team Server after the commit), wrapped round the steps in `steps.ts`. Routes: `http/routes/team-server.ts`. Pages: the wizard's `ui/wizard/new/repo-home-field.ts` (Where the code lives), ⚙️ Settings › ☁️ Team Server (`ui/team-server/`: the card and the Connect confirm step), the Overview's Portal app row and its Mendix Cloud rows, the Studio confirm's Team Server hints (`ui/studio/index.ts`) and Connections › Mendix's per-project link.

- **`answers/`** and **`dispatch/`** are durable answers and dispatch (Slice 1B-1). The answer store (`answers/store.ts`, `<data>/answers/<project>.jsonl`) appends every revision of a decision (an escalation, a BRD question, a stuck item, a proposal, a model change request, a tell) with its full text, hash-chained like the acceptance records and fsync'd: the history, which the audit log is not. The dispatch store (`dispatch/store.ts`, `<data>/dispatch/<project>.json`, the critical write, serialised per project) keeps each attempt to hand an answer on: the exact payload, the worker, its session and transcript offset, captured before typing, and its state (`prepared` → `in-flight` → `submitted` | `held` | `refused` | `failed`, or `outcome-unknown` until a person says `person-confirmed-sent`, `person-chose-resend` or `person-abandoned`). `dispatch/service.ts` runs every answer path in one order (stale check, claim, revision, intent, in flight, act, settle, then the decision's own record); `reconcile.ts` and `evidence.ts` settle what a restart left, from the recorded session only; `guard.ts` is the rollback guard (`agent-office dispatch status`, Restart safely's check). The roster's side is `roster/escalation-answer.ts`, `dispatch-send.ts`, `dispatch-hooks.ts`, `dispatch-person.ts` and `proposal-issue.ts`; the card is `ui/dispatch/`. The guarantee is durable intent plus reconciliation, and no automatic replay of an ambiguous attempt, never exactly-once.

- **`followthrough/`** is Recorded as given (Slice 1B-2). An answered decision's record is compared with what was decided before it reads *recorded as given*: a BRD question's fields against what each sent revision asked for (`questions/book.ts`, `shared/questions.ts` `expectedOf`, the values the message carried), an escalation's `Decided per ESC-<id> rev <n>: <answer>` line, whose answer part (after the colon, to the end of the line or cell) must be exactly the revision's option or words (`judge.ts`, on the asks look's reads through `asks/readers.ts`; the exact-answer rule and what it normalises are `shared/recorded-answer.ts`). A citation only locates; a record that mentions the decision without stating it exactly is *needs review*. `audit.ts` is the read-only historical check of findings made under the older substring rule. `locate.ts` says where the record is (path, commit, blob, working copy / branch / merged into `origin/<default>`), git off the event loop and cached. `service.ts` is the feed (`GET /api/followthrough`), Accept as recorded and Send correction (through the dispatcher), and the settled check stuck detection asks (`stuck/sources.ts`): only recorded as given at the current revision, merged into main, settles a decision with an answer revision. The page's half is `ui/followthrough/`.

- **`change-answer/`** is Change answer (Slice 1B-3). `service.ts` replaces an answered escalation's or a sent question's answer: revision n+1 (`supersedes: n`) through the dispatcher with the stale check (a 409, nothing written), a message that cites the new revision, and, once it settled, the decision's own record on n+1 with follow-through started again and rev n's finding kept (`store.ts`, `<data>/change-answer/<project>.json`). `links.ts` lists the work that used a revision from explicit links only (an escalation's `refs`, `Assignment.pending.escalationId`, `TaskVerification.escalationId`, recorded; a model change request's text and a BRD question's `blocks`, inferred). `pending.ts` keeps each change, and each 1B-2 Send correction, whose dispatch hasn't settled on disk before it is typed (`<data>/change-answer/<project>.pending.json`, the critical write) and hears the dispatcher through its `hooks`: typed (or It went through) moves the decision on, abandoned or not sent clears it with an audit line, unknown never moves it; `index.ts` sweeps what a restart left after the start's reconcile. Routes: `/api/answers/detail` and `/api/answers/change` (admins only, `http/routes/change-answer.ts`). The page's half is `ui/change-answer/` (the dialog, the history fold, the detail fetched once on open).

- **`tasks/`** is task identity and linked work (Slice 1B-4). `store.ts` is the task record, `<data>/tasks/<project>.jsonl`: append only, hash-chained like the answer store, a line per task made (`tsk_<ulid>`, its source, first line, issue, a queue task's old id as `legacyId`) and per event (assigned or reassigned with that attempt's `exe_<ulid>`, completed, cancelled, superseded). Minting is synchronous so the id is in the text before it is typed (`identify.ts`: an id already in the text, the open task of the issue it names, or a new one); the line goes to disk in order behind it. The roster's side is `roster/task-ids.ts` (a member's `Assignment` holds the ids, `prevTasks` is a cache), the queue's `queue.ts`, and `currentTaskIds` in `index.ts` is what a context manifest or a trace calls for a member's task and execution ids. The links from a decision revision to the work are `evaluate.ts` (candidate from the dispatch's captured task, associated from commits and PRs that name the revision or the task id, inferred from build-plan rows; evidence acknowledged, associated change, checks passed on the associated change, implemented as decided only by an acceptance record's `decisions`), fed by `links.ts` from what the office already keeps plus local git (`git.ts`, cached a minute), asked by Change answer's detail and peeked by the follow-through feed. The words are `shared/task-links.ts`; the page's half is `ui/task-links/`.

## Shared

- **`protocol.ts`** is the wire protocol. It puts the domain files in `protocol/<domain>.ts` back together (`export *`) and makes the `ClientMsg` and `ServerMsg` unions every frame is one of. Keep `import type` between domain files: some name each other's types (`floors.ts` and `presence.ts` do), which only type imports can do without a cycle at run time.
- **`providers.ts`** is the provider table: every agent a worker can run, and what the office knows about each.

The rest is data and pure code both sides use: the project's layout, maps (`shared/maps/`), the sun, the garage and so on.

## Adding a feature

A new feature adds files of its own and one line in each list it joins. For something on a project that everyone there sees, that's:

1. **Its messages** in a protocol domain file (`src/shared/protocol/<domain>.ts`). A new domain file also goes in `protocol.ts`: its `import type`, its `export *` and its members of the unions.
2. **A server handler file**, `src/server/ws/handlers/<name>.ts`, and its line in `handlers` in `ws/handlers/index.ts`. If it keeps something per person, its `FeatureHooks` go in `features` there; if people arriving on a project need its state, that's a field of `FloorView` (`protocol/floors.ts`) and its piece in `views`. What a project keeps is a module of its own in `src/server/`, which `Floor` makes.
3. **A state slice**, `src/client/state/slices/<name>.ts`, and its line at the end of `SLICES` in `state/slices/index.ts`.
4. **Its window or panel** in `src/client/ui/<name>/` (or `ui/<name>.ts`), opened from the page that shows it: a tab of the 1D view (from the tab registry, see [Adding a project tab](#adding-a-project-tab)), an item of the ☰ menu (`shared/flatmenu.ts`), or something to click in the 2D Office view (`pixel/hotspots.ts`).
5. **Its CSS** next to its ui module, imported from there, in the color tokens.

Its HTTP routes, if it has any, go in `http/routes/`, and its tests in `tests/`.

## Adding a project tab

A page of the 1D view (a project tab, `/lite?tab=<id>`) is a module of the feature's own that calls `registerTab` (`src/client/tabs/registry.ts`), plus its import line in `src/client/tabs/index.ts`. Nothing in `lite.ts`, `lite.html` or the navigation's list (`ui/portal/nav-logic.ts`) changes. 🧪 Tests (`ui/testlab/tab.ts`) is one:

```ts
import { registerTab } from '../../tabs/registry';
import { testlabView } from './index';

registerTab({
  id: 'tests', // ?tab=tests, its container #tests-view
  group: 'monitor', // the navigation group it's in
  label: 'Tests', // the item and the page header's title
  tooltip: 'Test mode: the suites, their runs and results', // the header's line under the title
  admin: true, // only admins see it in the navigation
  mount: (container) => testlabView(container), // gives back { show?, hide?, refresh? }
});
```

- **The navigation** (`navGroups()` in `nav-logic.ts`) puts it in its group: the built-in items are at 10, 20, 30… in their order, a tab with `order` goes where that puts it (15 is after the first), and one without goes after the built-in items, in the order the index registers them. `navItem`, `groupOf`, `pageTitle`, `visibleItems` (admin-only tabs for admins only), the search and the remembered open groups know it like any other.
- **The address**: `asTab` takes `?tab=<id>` and the tab a reload keeps, so deep links work; an id that isn't a tab still opens the Command Center.
- **The page** (`tabs/host.ts`, which `lite.ts` calls once) gives each registered tab an empty, hidden `#<id>-view` before the Agents' view at start and nothing more: `mount` runs the first time the tab shows. From then on every `showTab` calls its `show` when it's the tab asked for and its `hide` when it isn't, and `refresh` when the project changes while it's showing. `tabRow: true` (with an `icon`) also gives it a button in the classic themes' tab row; without it the Portal navigation, links and the ☰ reach it.
- An id must be lower case and not a built-in tab's or action's (`registerTab` throws).
- `hidden: true` keeps a tab out of the navigation (and its search) while `?tab=`, the header's title and `openProjectTab` (`tabs/host.ts`) still reach it: the Developer view's four inner sections are such tabs, its own section bar their navigation.
- **Something beside every tab** rather than a tab of its own (the team-lead panel, `ui/lead-panel/`, docked on the right of every project page) is mounted once by the page and follows the tabs with `onProjectTab(fn)` from `tabs/host.ts` (every tab `showTab` shows, built-in or registered, and the one showing now): nothing in `showTab` for it, and a tab change never touches its state. A view that docks it beside its own canvas (the Developer view) lends it a header, cards in the conversation and context chips through `ui/lead-panel/dock.ts` (`setPanelDock`, `focusDock`, `dockSelection`): the same panel and conversation, no second chat.

## Adding an agent provider

One adapter file in `src/server/providers/`, one entry in `PROVIDERS` in `src/server/providers/index.ts`, and one row in `src/shared/providers.ts` (its id in `AGENT_PROVIDERS`, its entry in `PROVIDER_META`). The typecheck fails until all three are there. Its row says which models and efforts it takes and how the hire dialog asks for them; one whose CLI lists its models gets a lister in `src/server/models.ts` too. What reads them, and the one place that still names providers one by one, are in [Provider seams](dsh-acp-integration.md#provider-seams).

## The size guard

`tests/size.test.ts` holds every `.ts` and `.css` file under `src/` to 600 lines. It asks `git ls-files` for them (tracked, and new ones that aren't ignored) rather than walking the folder, so a worktree checked out inside the repo can't trip it. The files that were longer when it came in are listed in `CEILINGS`, each with the length it had then: they may shrink, but never grow past it. Once one is down to 600 lines or fewer, or gone, the test fails until you take it off the list, so the list only gets shorter.

When it fails, split the file along the registries: a feature's code goes in its folder, a message handler in its domain's file, a tick or a key in the feature it's for, and what the page keeps of it in its own slice. Raising a ceiling, or adding a file to the list, only hands the problem to the next person, so the honest way to make room is to split the file. When you shrink a listed file, lower its ceiling to its new length in the same change, so it can't grow back.
